# data.txt 同期の仕組み

## 1. 登場人物と責務

```
ブラウザ(複数)  <--WebSocket-->  Hub (collab)  <--Text()/Replace()-->  Syncer (filesync)  <-->  data.txt
 CodeMirror                       履歴 + 文書                            lastSynced
```

| 部品 | 持つ状態 | 責務 |
|---|---|---|
| ブラウザ | 同期済みバージョン、未確認の自分の更新 | 編集、push、受信した更新のリベース |
| Hub | `updates`(受理済み更新の履歴)、`doc`(履歴を全部適用した結果) | 更新の順序付け、検証、配信 |
| Syncer | `lastSynced`(最後にファイルとバッファが一致した内容) | ファイルとバッファの橋渡し |

`Syncer` は `Hub` の内部を知らず、`Text()` と `Replace()` の2つだけを使います。

## 2. 前提: codemirror/collab のルール

- **バージョン = 履歴の長さ。** サーバが受理した更新の総数が、そのまま現在のバージョンです。
- クライアントは「同期済みバージョン」と「未確認の自分の更新」を持ちます。
- クライアントは `push {version, updates}` を送ります。
  - `version == len(h.updates)` なら受理され、全員に配信されます。
  - `version < len(h.updates)` なら受理されず、足りない更新が返ります。クライアントは `receiveUpdates` で自分の未確認更新をそれらの上にリベースし、再度 push します。

つまり**競合解決はクライアントのリベースに任せ、サーバは順序を決めるだけ**です。この設計に、ファイルの変更を乗せています。

## 3. ファイル → 編集バッファ(上書きの仕方)

ファイルが外部で書き換えられると、サーバは**サーバ自身が書いた通常の更新**として履歴に追記します。

```
Replace(text)
  1. 現在の doc と新しい text の最小差分を求める (replaceChanges)
  2. それを ChangeSet JSON にする
  3. clientID: "server" の Update として履歴に追加し、全クライアントへ配信する (accept)
```

`clientID: "server"` は本物のクライアントIDと一致しません。そのため、クライアントは**他人の更新**として受け取り、自分の未確認の編集をその上にリベースします。新しいメッセージ種別もクライアント側の変更も不要です。

### 例

バッファが `abcd` で、外部プロセスがファイルを `abXcd` にした場合:

```
共通接頭辞 "ab" (2) / 共通接尾辞 "cd" (2) / 中間は 0文字削除 + "X" 挿入
=> [2,[0,"X"],2]
```

ChangeSet の書式は次のとおりです。

- 数値は「その文字数を保持」を表します。
- `[n, "行1", "行2"]` は「n文字削除し、行を改行区切りで挿入」を表します。

### 全置換にしない理由

全置換 `[[4,"abXcd"]]` にすると、全員のカーソルが置換範囲に巻き込まれて移動します。最小範囲にすると、フロントの `cursorsField` が `tr.changes.mapPos` で位置を追従させるので、離れた場所のカーソルは動きません。

### 位置の単位(UTF-16)

CodeMirror の位置は UTF-16 コードユニット単位です。絵文字は2、日本語は1です。サーバは `doc` を `[]uint16` で持ち、同じ単位で適用します。差分の境界がサロゲートペアの途中にならないよう、接頭辞・接尾辞を1つ戻す処理を入れています。

## 4. 編集バッファ → ファイル(自動保存)

保存は2つのきっかけで同じ `sync()` を呼びます。

- 1秒ごとのティッカー
- fsnotify のイベント(100msデバウンス後)

デバウンスは、1回の書き込みで複数イベントが出ることと、書き込み途中を読んでしまうことを避けるためです。イベントのたびに待ち時間をリセットします。

保存は同じディレクトリに一時ファイルを作り、fsync してから rename します。外部プロセスが半端な内容を読むことはありません。ファイル単体ではなく**ディレクトリ**を監視するのは、rename による置換で inode が変わるとファイル単体の監視が外れるためです。

## 5. 核心: `sync()` の判定ルール

`lastSynced` は、「ファイルとバッファが最後に一致した内容」です。

```
fileText = ファイルを読む (CRLF→LF 正規化)

[1] ファイルが存在し、fileText != lastSynced
      → 他者が編集した。ファイルの勝ち
      → lastSynced = fileText; Replace(fileText)

[2] ファイルが存在し、バッファ == lastSynced
      → 何も変わっていない。終了

[3] それ以外 (バッファが先に進んだ / ファイルが無い)
      → バッファをファイルへ保存; lastSynced = バッファ
```

| 状況 | ファイル | バッファ | 結果 |
|---|---|---|---|
| 変更なし | = lastSynced | = lastSynced | [2] 何もしない |
| ユーザが打鍵 | = lastSynced | ≠ lastSynced | [3] 保存 |
| 外部編集 | ≠ lastSynced | 何でも | [1] ファイルが勝つ |
| ファイル削除 | 無い | 何でも | [3] 復元 |

### なぜ「ファイル == バッファ」で判定しないのか

保存の直後、次の保存の前にユーザが1文字打ったとします。

```
保存:   ファイル "a",  バッファ "a",  lastSynced "a"
打鍵:   ファイル "a",  バッファ "ab", lastSynced "a"
```

「ファイル ≠ バッファ」だけを根拠にすると、これを外部編集と誤認し、ファイルの内容 `a` でバッファを上書きして**打鍵が消えます**。`lastSynced` と比べれば、ファイルは `a` のままなので「誰も触っていない」と判定でき、バッファの `ab` が保存されます。

### 自分の書き込みでループしない理由

自動保存でファイルを書くと fsnotify が発火します。

```
保存 → lastSynced = 書いた内容 → fsnotify発火 → sync()
     → ファイル == lastSynced なので [1] に入らない
     → バッファが同じなら [2] で終了
```

取り込み([1])でも `lastSynced = fileText` にするので、取り込み後の `sync()` はファイルを書き戻しません。取り込み → 保存 → 通知 → 取り込み、というループは起きません。

## 6. 競合の解決ルール一覧

| 競合 | 解決 |
|---|---|
| 複数ユーザの同時編集 | collab の標準動作。サーバが順序を決め、遅れたクライアントはリベースして再送 |
| 外部編集とバッファの未保存編集 | **ファイルが勝つ**。最大1秒分の未保存編集は失われる(仕様) |
| 外部編集と、入力中のクライアント | サーバの更新が先に履歴に入り、クライアントの push は拒否され、受け取ってリベースして再送。内容が混ざることはあるが壊れない |
| 保存直前の外部編集 | `sync()` は先にファイルを読むので、[1] が優先され、保存せず取り込む |
| 保存中の打鍵 | 書き出すのは `Text()` の時点のスナップショット。打鍵は次の `sync()` で保存される |
| ファイル削除、一時的な欠落 | 次の `sync()` で復元。vim の保存途中の欠落はデバウンスで吸収 |
| CRLF | 取り込み時に `\n` へ正規化。バッファを編集するまでファイルは書き換えない |
| vim が末尾に改行を足す | 1回取り込まれて収束する(`lastSynced` が更新されるので書き戻さない) |
| 不正な更新(長さ不一致など) | 履歴に入れず、接続を切って理由をクライアントに表示 |

### 残っている小さな競合の窓

`sync()` がファイルを読んでから rename するまでの数ミリ秒の間に外部編集が入ると、その編集を上書きします。1秒に1回、ごく短い窓なので、概念実証としては許容しました。完全に塞ぐには、書き込み直前にもう一度ファイルを読んで比較する方法があります。

## 7. ロックと並行性

- `Syncer.mu`: `sync()` 全体を直列化します。ティッカーとデバウンスが同時に走っても、判定の途中で `lastSynced` が変わりません。
- `Hub.mu`: `Text()`、`Replace()`、push の内部だけで取ります。
- **ロック順序は `Syncer.mu` → `Hub.mu` のみ**で、逆はありません。
- ファイルI/Oは `Hub.mu` の外で行うので、ディスクが遅くても WebSocket の配信は止まりません。

## 8. 起動と再起動

- 起動時に `Start` が1回 `sync()` を呼びます。`lastSynced` は `""` なので、ファイルに内容があれば [1] で取り込まれ、履歴の先頭に `server` の更新が入ります。
- クライアントは「空の文書から履歴を再生する」ので、再接続すると同じ内容を復元できます。
- 履歴は永続化しません。サーバを再起動すると履歴は作り直されるため、開いたままのブラウザは `invalid version` で切断されます。リロードで復帰します(現在のエラー表示のまま)。

## 9. 動かして確認する手順

```
make dev-back
```

別ターミナルで次を試すと、各ルールを体感できます。

```
echo "hello" > data.txt          # [1] 外部編集がバッファを上書きする
printf 'a\r\nb' > data.txt       # CRLFが正規化される (ファイルは書き換わらない)
rm data.txt                      # 1秒以内にバッファの内容で復元される
```

ブラウザで編集して `cat data.txt` を繰り返すと、1秒以内に保存される様子も確認できます。ブラウザを2枚開き、片方の文頭にカーソルを置いたまま `data.txt` の末尾だけを書き換えると、カーソルが動かないことも見られます。

## 10. まとめ

- 外部編集は「サーバが書いた通常の更新」にして流す。collab のリベースがそのまま使えるので、プロトコルの変更は不要。
- 外部編集かどうかは `lastSynced` で判定する。バッファとの比較は、打鍵を消す危険があるので使わない。
- 衝突したら常にファイルが勝つ。それ以外の競合は collab のリベースが解く。
