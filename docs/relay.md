
## 要求
現在のサーバ起動モードの他にrelayコマンドでリレーサーバを起動できるようにしたい。
これは、serveコマンドで起動しているものと通信できるようにする。
relayはいわばプロキシサーバである。メインサーバは、特定のプロキシサーバをクライアントとして認可し、プロキシサーバ経由での編集ができるようにしたい。

サーバ間通信は当然websocket通信を行う必要がある。
リレーサーバ側で公開鍵暗号ed25519の鍵ペアを生成し、そこで生成した公開鍵をメインサーバ側に何らかの手段で受け渡す。メインサーバは認可した公開鍵の編集のみを許可するようにする。

PoCでは、authorized_keys ファイルにリレーサーバの公開鍵を登録し、リレーサーバの秘密鍵は、
relay-private.pem に配置する


## 推奨構成: 1ブラウザ = 1アップストリーム接続の透過パイプ

```
ブラウザ --ws--> relay --ws(署名付き)--> メインサーバ /connection/relay --> Hub
        /connection/collab              認証ミドルウェア → Hub.ServeHTTP
```

- relay はブラウザから WebSocket を受けるたびに、メインサーバへ接続を1本張ります。その際、署名付きヘッダを付けます。
- 以降はメッセージを中身を見ずに双方向へ転送するだけです(`push` / `updates` / `cursor` / `leave` はそのまま通ります)。
- Hub から見ると、ブラウザは今まで通り独立したクライアントです。`clientID` やカーソル、`leave` の通知、履歴の再生がすべて変更なしで動きます。
- relay も同じバイナリで静的ファイル(`static.FS`)を配信するので、フロントの `collabURL()` も変更不要です。
- メインサーバには認証必須の `/connection/relay` を新設します。認証を通ったら既存の `Hub.ServeHTTP` に渡すだけです。
- 1本に多重化する案は、仮想クライアントIDのフレーミングや Hub 側の改修が要り、複雑になるので見送ります。ブラウザ数が増えて接続数が問題になったときに再検討すれば十分です。

## 認証方式(ed25519)

WebSocket のアップグレード要求のヘッダで認証します。

- relay は「自分の公開鍵・UNIX時刻・署名」を送ります。署名対象は `"myapp-relay-v1\n" + 時刻 + "\n" + リクエストパス` で、プレフィックスは用途分離のためです。
- サーバは次の順で検証し、失敗すれば Upgrade 前に 401 を返します。
  1. 時刻が ±30秒以内か
  2. 公開鍵が `authorized_keys` にあるか
  3. 署名が正しいか
- 401 の本文は原因が分かる文言にします(未登録の鍵、時刻ずれなど)。relay はそれをブラウザの close reason に載せるので、既存の「エラーはユーザに見せる」方針と揃います。
- 代替案はチャレンジ・レスポンス(サーバが nonce を送る方式)です。リプレイには強いものの、Hub の接続処理に認証状態が入ります。単純さを優先してヘッダ方式を推奨します。後から差し替え可能です。

## 鍵とファイル

- **`relay-private.pem`**: PKCS#8 PEM で、標準ライブラリだけで読み書きできます。0600 で作成します。
- **`authorized_keys`**: OpenSSH 形式 (`ssh-ed25519 AAAA... comment`) を推奨します。`golang.org/x/crypto/ssh` を1つ追加すれば、パースの自前実装が不要になります。`ssh-keygen -y -f relay-private.pem` でも公開鍵を取り出せます。依存を増やしたくなければ、素の base64 1行にする手もあります。
- メインサーバは**接続ごとに `authorized_keys` を読み直します**。ファイルが小さいので、ウォッチャも状態も不要で、追加が再起動なしで反映されます。ファイルが無ければ全拒否にします。
- 鍵の生成は明示的な `keygen` コマンドにします(既存ファイルは上書きしません)。自動生成だと、パスの打ち間違いで別の鍵ができて原因が分かりにくくなります。公開鍵の1行は keygen の出力と relay 起動ログの両方に出し、コピーし忘れても困らないようにします。
- `.gitignore` に `relay-private.pem` を追加します。

## コマンドとファイル構成

現状の `main.go` にはサブコマンドがありません(Makefile の `serve` は旧テンプレートの名残です)。標準ライブラリの `flag.FlagSet` で最小限の振り分けを入れます。

- `myapp serve [--addr] [--authorized-keys]`: 既存の動作に加え、`/connection/relay` を追加します。
- `myapp relay --upstream ws(s)://host:port [--addr] [--key]`
- `myapp keygen [-o relay-private.pem]`

パッケージは次のとおりです。

- `internal/relayauth`: 鍵の生成と読み込み、署名、検証、`authorized_keys` のパース、認証ミドルウェア
- `internal/relay`: プロキシハンドラ(close コードと理由の双方向伝播を含む)
- `cmd/myapp`: `serve.go` / `relay.go` / `keygen.go`

テストは署名と検証(期限切れ、未登録の鍵、パス改ざん)、`authorized_keys` のパース、`httptest` でのプロキシ疎通と close reason の伝播を書きます。規模は Go で300行前後の見込みです。

## 把握しておくべき制約

1. **署名は通信を暗号化しません。** 認証後の WebSocket フレームは平文のままで、第三者による乗っ取りも防げません。relay とメインサーバの間は本番では `wss`(リバースプロキシで TLS)にする必要があります。ヘッダ方式のリプレイ窓(30秒)も、TLS があれば実害はありません。
2. **鍵が認証するのは relay であり、エンドユーザではありません。** いまはログインが無いので、relay に到達できる人は誰でも編集できます。relay の公開範囲がそのまま編集権限の範囲になります。ユーザ認証が必要になったら relay 側に足す話です。
3. **鍵を削除しても、既存の接続は切れません。** 新規接続だけが拒否されます。即時に切るには、鍵ごとの接続管理とファイル監視が要るので、PoC では許容します。
4. メインサーバの待ち受けが `127.0.0.1:3002` に固定されているので、別ホストの relay から繋ぐには `--addr` の指定が必要です。

## 今回の仮定


- 既存の `/connection/collab` は認証なしのまま残します。
- 認可された鍵は全員が編集可能とし、読み取り専用などの権限差は設けません。
- relay の待ち受けは、メインサーバとは別ポートにします。
